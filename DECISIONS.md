# PokerGym — DECISIONS.md

**Версия: v1**

Технические и продуктовые решения по проекту — что решено и почему. Хронология конкретных находок и багов живёт в git (сообщения коммитов), здесь — только действующие правила и контракты. Ссылки на ID компонентов — см. таблицу в `ARCHITECTURE.md`.

## Разбиение на файлы — общие правила
- ES-модули, не `<script>`-теги. `import` не работает на `file://` — нужен локальный сервер при разработке.
- **Правило самодостаточности.** Каждый переданный результат — пара «вынесенный кусок + обновлённый остаток, который на него ссылается», никогда кусок сам по себе (реальный инцидент: CSS был вынесен без переписанного `index.html` — «проверка» ничего не проверяла). Единица работы — наименьший набор файлов, при котором результат реально запускается и тестируется, не обязательно один файл из таблицы.
- Три отдельных роутера, не один: `router.js` (вкладки + «назад», общий), `practice/practice-router.js` (под-экраны Практики), `theory/theory.js` (под-разделы Теории).
- `core/state.js` — чистое хранилище, без импортов из фич-модулей (риск циклических зависимостей). Другие модули подписываются на изменения сами, не наоборот.
- `practice/trainings/` — плоская папка: без подпапки на каждую тренировку, без группировки по категориям хаба (та классификация — UI/педагогическая, не структура кода).
- `-logic.js`/`-ui.js` — только для тренировок заметно больше ~150–200 строк; сейчас ни одна не разделена (см. Backlog в `ARCHITECTURE.md`). Критерий чистоты: если в логике встречается `document.getElementById`/`innerHTML` — код не в том файле.
- Перед написанием кода новой тренировки — сначала проверить `core/`/`ui/`, не копировать, если похожее уже есть.

## Методология проверки
- `node --check файл.js` (без флагов) ненадёжен для ES-модулей — может показывать «всё чисто» на файлах, которые падают в браузере. Использовать `node --input-type=module --check < файл.js`.
- Этого тоже недостаточно — не ловит несовпадение импорт/экспорт и логические ошибки. Обязательна полная имитация браузера через `jsdom` (загрузка настоящего `index.html`, реальные клики по интерфейсу) перед сдачей любого объединяющего шага.
- **Не мутировать массив, на который могут ссылаться другие места, без `.slice()`.** `shuffle()` (Фишер-Йетс) меняет переданный массив на месте. Если передать общую константу напрямую (как было с `POS_LADDER_OLD[n]`) — она необратимо портится при первом же вызове, и баг проявляется не сразу, а спустя один-два раунда/переиспользования. Тасовать копию: `shuffle(arr.slice())`, если исходный массив используется где-то ещё.

## Контракты, зафиксированные при интеграции
- **Роутер — реестр коллбэков, не прямые импорты.** `onSubviewShow(name, fn)` / `onAnySubviewShow(fn)` в `practice-router.js`: тренировка сама регистрирует, что делать при показе своего экрана. Роутер не импортирует тренировки напрямую — иначе циклический импорт (тренировки и так импортируют `showSubview` из роутера).
- **`ui/card.js`: `cardEl(card, faceUp, faceStyle, cardBack)`** — стиль колоды и рубашка параметрами, файл не импортирует `core/state.js`.
- **`core/session.js` — чистый стейт-менеджер, без DOM.** `createSession`/`recordAnswer`/`isSessionComplete`. Формат результата хода:
  ```js
  { trainingId: string, isCorrect: boolean, userAnswer: any, correctAnswer: any, timestamp: number }
  ```
  Подготовлен и проверен, но пока не подключён — `outs.js`/`positions.js`/`combinations.js` считают счёт по-старому, чтобы не менять поведение попутно с переносом файлов. Понадобится к Этапу 5 (Статистика).
- **`core/equity-worker.js`** — модульный воркер (`{ type: 'module' }`), импортирует `hand-eval.js`/`deck.js` напрямую, без дублирования кода. Путь к самому файлу воркера считается на стороне `calc-equity.js`, через `new URL('../../core/equity-worker.js', import.meta.url)` — не жёсткий путь, не сломается при деплое в подпапку (например, GitHub Pages без своего домена).
- **`evaluate7` переименована в `evaluateBest`** — функция универсальна для 5/6/7+ карт через `combinations(cards, 5)`, не жёстко на семь.
- **Калькулятор аутов не делит состояние с тренировкой «Ауты».** В оригинале — общие переменные `currentDeal`/`currentClassification` (общая область видимости позволяла). Теперь — собственные `calcCurrentDeal`/`calcCurrentClassification`, поведение калькулятора не изменилось.
- **DTO раздачи для Обучариума.** Функции генерации раздачи (`dealNewHand`, `dealNewPositionsRound`, `dealNewCombo` и т.п.) при следующей содержательной правке каждой конкретной тренировки должны получить опциональный параметр «готовая раздача извне» — не сделано ещё ни в одной, закладывать по одной, не разом.
- **Точка входа для Обучариума — `startTraining(moduleId, customSettings)` — контракт описан, механизм не построен.** Что конкретно должна принимать каждая тренировка — см. `ARCHITECTURE.md`, конец раздела «План игры». Когда `customSettings` заданы — шестерёнка настроек на экране тренировки не показывается.

## `ui/`-компоненты — что вынесено, что решено не выносить
- `answer-options.js`, `table-seats.js`, `range-grid.js` — **решено не выносить.** Исходный код в трёх местах не «глупый» (читает состояние своей тренировки напрямую — `posState`/`comboState`), настоящая параметризация — отдельный редизайн без доказанной второй точки применения. Код остаётся внутри тренировок, если не появится конкретная новая причина вернуться к вопросу.

## UX: экран настроек тренировки
- Тренировка открывается сразу в режиме сессии (настройки по умолчанию/сохранённые), настройки — через шестерёнку и модалку поверх экрана, без отдельного экрана сетапа первым. Упрощает `practice-router.js` — не нужна пара setup/session под-экранов на каждый модуль. Финальное подтверждение перед реализацией — за Романом, это продуктовое решение.

## Web Worker и SortableJS — ES-модули
- Воркер создаётся как модульный (`new Worker(url, { type: 'module' })`), не через `importScripts`.
- SortableJS подключается через официальную ESM-сборку из npm-пакета (`sortable.esm.js`), не через CDN и не классическим `<script>`.

## Работа с репозиторием из чата (без Claude Code)
- Project Knowledge (Документы проекта) не годится для активно редактируемого многофайлового проекта: либо грузит всё целиком в контекст ниже ~200К токенов, либо нечёткий RAG-поиск выше. `ARCHITECTURE.md`/`DECISIONS.md` — небольшой ориентир там, сам код — точечно.
- Рабочий способ чтения кода: `bash_tool` (обычный `curl`), не `web_fetch`. `web_fetch` может читать только уже встречавшиеся в разговоре URL — ограничение безопасности, действует с момента появления инструмента. `bash_tool` — отдельная песочница с доступом к `github.com`/`raw.githubusercontent.com`/`api.github.com`/`codeload.github.com` без этого ограничения:
  ```
  curl -s "https://raw.githubusercontent.com/Ramzesikus/PokerGym/main/путь/к/файлу"
  ```
  `api.github.com` (список файлов одним запросом) подвержен общему лимиту запросов на IP — при отказе просто повторить позже, или сразу читать файлы напрямую через `raw.githubusercontent.com`. Требует публичного репозитория.

## Claude Code
- Работает напрямую с файлами на диске, `CLAUDE.md` в корне читается автоматически. Доступен из терминала, десктоп-приложения, браузера, мобильного приложения. Рекомендуется изоляция при автономном режиме — простаивающая VM с Ubuntu в VirtualBox. Сессия не видит переписку в обычном чате. Пока не переходим.

## PWA
- PWA = сайт + `manifest.json` + service worker. Сейчас ни того, ни другого нет. Известная болячка — обновление закэшированной версии без продуманного версионирования. Поддержка PWA у Apple менее стабильна, чем у Google/Android.

## Деплой
- Деплой происходит по `git push`, не по каждому визиту. Публичность репозитория и публичность сайта — независимые вещи. Минификация — часть сборки, которой сейчас нет в проекте. Файлы репозитория при деплое остаются нетронутыми.

## Приватность репозитория
- Публичный репозиторий, пока в нём только клиентская логика — риск низкий. Автоматические боты сканируют все публичные репозитории на предмет секретов — секреты не коммитить никогда. Закрыть репозиторий — когда появится код авторизации/оплаты.

## Целевая архитектура ресурсов
- Три слоя: хостинг статики → сервер API → база данных. Начинать с управляемых отдельных сервисов, не с одного своего сервера.

## localStorage
- Формат — JSON. Чисто локальные предпочтения (язык, тема, порядок хаба) — только `localStorage`. Данные аккаунта (подписка, прогресс, статистика) — источник правды сервер/БД, `localStorage` — кэш для офлайн/скорости, синхронизация при подключении. Сейчас `localStorage` не существует вообще.

## Защита
- Обязательная (пароли/HTTPS/токены/платёжный провайдер) — стандартные средства. Защита от копирования — принципиально не стопроцентная. Стратегия: «сделать бесполезным без сервера», не «сделать невозможным» — ценная логика (генератор Обучариума) переносится на сервер. Конфликт целей: офлайн-режим vs частая ревалидация лицензии — компромисс, ограниченный офлайн-срок. Простая мера сейчас — лимит одновременных сессий. Водяные знаки — отложено до признаков реальной проблемы. Юридическая мера — пользовательское соглашение. Общая калибровка: серьёзная защита кода — практика крупных игроков в конкурентных нишах, для небольшого продукта — дешёвый минимум сейчас, дорогие меры по факту необходимости.

## App Store / Google Play
- Android — TWA, Bubblewrap/PWABuilder, 80+ баллов Lighthouse, 25$ разово. iOS — менее стабильная поддержка PWA у Apple, реалистично нативная обёртка с WebView, 99$/год, решение отложено.

## Хранение пользовательских данных
- Внутренние данные приложения (статика) vs внешние данные пользователей (сервер+БД) — разная инфраструктура. Пароли — только хешированные. Открытый вопрос: требования 152-ФЗ о хранении персональных данных в РФ — проверить отдельно, не юридическая консультация.
