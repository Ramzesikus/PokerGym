# PokerGym — ARCHITECTURE.md

**Версия: v5**

Нумерация версий: первая содержательная правка после начала работы над Этапом 1 стала v1, и далее по нарастающей. Версия указывается только внутри самого файла — имя файла остаётся неизменным (`ARCHITECTURE.md`), историю версий ведёт git (`git log -- ARCHITECTURE.md`), а не суффикс в имени.

Это живой документ. Обновляется по ходу разработки, не разовый снимок. Версия увеличивается на 1 при каждой содержательной актуализации файла (не при мелких точечных правках вроде переименования одного ID).

**Важная дисциплина:** таблица в разделе 1 всегда отражает *текущее* состояние репозитория, а не план. Всё, что ещё не написано — в разделе 3 (План игры / Backlog). Когда часть работы запушена на GitHub — таблицу нужно попросить обновить.

Источник для таблицы: `poker-trainer_v15_35.html` (7012 строк, один файл, ещё не разбит — разбиение только спланировано).

## 2. DECISIONS — журнал решений

### Разбиение на файлы — общее
- Переходим от одного `index.html` к структуре файлов по функциональным швам — не тратить токены на весь проект целиком, не терять возможность оценивать результат в совокупности.
- **ES-модули**, не обычные `<script>`-теги. `import` не работает на `file://` — нужен локальный сервер при разработке.

### Методология проверки — исправлена после реального провала
- **`node --check файл.js` (без флагов) оказался ненадёжным индикатором для этого проекта — систематически показывал «всё чисто» на файлах, которые реально падали в браузере.** Причина: без `--input-type=module` он не всегда проверяет файл как настоящий ES-модуль. Обнаружено только когда Роман открыл собранное приложение в браузере и получил пустой экран без единой рабочей кнопки — то есть на практике, не в теории.
- **Правильная проверка синтаксиса:** `node --input-type=module --check < файл.js` — так действительно ловит несовпадение скобок и прочие структурные ошибки.
- **Но и этого недостаточно** — синтаксис может быть идеальным, а импортированное имя реально не экспортировано целевым файлом, или функция вызывает то, что не импортировала. Это ловится только полной имитацией браузера. Настроена через `jsdom` (реальный `index.html` загружается, `app.js` импортируется по-настоящему, кликаются реальные кнопки, проверяется реальный DOM после каждого действия) — это и есть тот уровень проверки, который нужно было делать с самого начала, а не полагаться на синтаксис.
- **Итог прогона через `jsdom` — найдено и исправлено 12 реальных багов**, ни один из которых не ловился синтаксической проверкой: недостающие фигурные скобки (`notation.js` — дважды, `theory.js` — дважды), полностью потерянное тело функции (`notHandCombos`), константы и функция, застрявшие не в том файле (`pfTokenSwitch` и другие — physически лежали в `notation.js`, нужны только `preflop-grid.js`), и семь случаев забытых импортов между файлами (`showSubview`, `SUITS`, `RANK_VALUE`, `cardId`, `cardEl`, `suitColor`, `backBtn`/`headerTitle`, `updatePosFormatAvailability`/`posState`-логика при смене языка).
- **Проверено вживую через клики (не только загрузка):** все 5 вкладок, все 6 реальных тренировок (открытие + запуск сессии), кнопка «назад» из тренировки и из «Теории», поиск по глоссарию, компакт-режим хаба, переключение языка и темы в настройках. Везде чисто, без единой ошибки в консоли.
- **Не проверено даже сейчас:** визуальный вид (расположение, цвета, анимации — `jsdom` не рендерит CSS), реальный `Worker` в браузере (в `jsdom` заглушен), сенсорные жесты и drag-and-drop карточек хаба. Это по-прежнему требует реального браузера от Романа.

### Уточнение статуса «глупых» компонентов (было упущено при предыдущей сдаче, фиксирую явно)
| Файл | Статус |
|---|---|
| `ui/card.js` | Полностью «глупый» — ничего не читает из `state` сам |
| `ui/card-picker.js` | Частично — `state.faceStyle`/`state.cardBack` читает напрямую, сознательно (грид на весь экран, параметризация каждой ячейки была бы избыточной) |

### Итог интеграции — index.html полностью на ES-модулях (что реально решилось по ходу сборки)
- **Три архитектурных проблемы, не предвиденные заранее, решены единообразно:**
  - `showSubview`/`showTheorySubview` в оригинале напрямую звали функции хаба/калькуляторов (`renderHub`, `renderCalcOutsResultText`, `eqRenderAll`) — с ES-модулями это дало бы циклический импорт (эти файлы сами импортируют `showSubview`). Решение — **реестр коллбэков** в `practice-router.js` (`onSubviewShow(name, fn)`, `onAnySubviewShow(fn)`): тренировки сами регистрируют, что делать при показе своего под-экрана, роутер не импортирует их напрямую.
  - Калькулятор аутов в оригинале **физически делил** переменные `currentDeal`/`currentClassification` с тренировкой «Ауты» (общая область видимости позволяла). В ES-модулях импортированную переменную нельзя переприсваивать — калькулятору даны собственные `calcCurrentDeal`/`calcCurrentClassification`, поведение не изменилось.
  - `applyLanguage` в `settings.js` — самая связанная функция во всём приложении, трогает разом Ауты, Комбинации, хаб, Теорию. Решена набором узких именованных экспортов (`refreshLanguageDisplay`, `refreshAnswerAreaIfActive`, `refreshCardFacesIfActive` и т.п.) из соответствующих файлов — проверено, что ни один из них не импортирует `settings.js` обратно, циклов нет.
- **Реальная ошибка, найденная и исправленная до передачи файлов:** `currentDeal`/`timerHandle` были только упомянуты в комментарии `core/state.js` («останутся локальными в outs.js»), но не были фактически объявлены (`let`) внутри `outs.js` — в строгом режиме ES-модулей это была бы `ReferenceError` при первом же присваивании. Добавлены явно.
- **Ещё уточнения границ, которых не было в таблице до сборки:**
  - «Матрица префлопа» кончается на строке 5618, не 5672 — с 5619 начинается «Позиции» (включая `POS_SEAT_COORDS`, `POS_LADDER_OLD/NEW`).
  - «Позиции» кончаются на 6016, «Комбинации» — с 6017, не с 6030.
  - Переключатель улицы (Флоп/Тёрн) для сетапа «Аутов» и блок поиска по глоссарию «Теории» были физически зажаты между «Комбинациями» и настройками — обе находки перенесены на верное место (в `outs.js` и `theory.js` соответственно).
  - «Комбинации» напрямую переиспользуют генератор раздач «Аутов» (`pickTargetCategory`, `generateCardsForCategory`) — экспортированы из `outs.js`.
- **Сознательно отложено, не потеряно:** `ui/answer-options.js`, `ui/table-seats.js`, `ui/range-grid.js` не вынесены — при попытке сборки выяснилось, что исходный код не «глупый» (читает `posState`/`comboState` напрямую), нужен настоящий редизайн под коллбэки, не механический перенос. Их код остаётся внутри `positions.js`/`combinations.js`/`preflop-grid.js` до отдельного захода. Разделение каждой тренировки на `-logic.js`/`-ui.js` тоже отложено на будущее — сейчас каждая тренировка один файл, ради скорости получения рабочего приложения целиком.
- **`core/session.js` подготовлен, но не подключён.** Существует, проверен в `test-core.html`, но `outs.js`/`positions.js`/`combinations.js` по-прежнему используют свои старые способы счёта — переключение на `session.js` не сделано в этом заходе, чтобы не менять поведение попутно с переносом файлов.
- **Автоматическая проверка перед сдачей** (не полагаясь только на `node --check` по отдельности): все относительные пути `import` во всех 29 файлах разрешаются в реально существующие файлы; циклических импортов между модулями нет; 28 из 29 файлов достижимы из точки входа `js/app.js` (`core/equity-worker.js` загружается отдельно, через `new Worker()`, не `import`). **Не проверено** — фактический рендер и работа в браузере (нет браузера в песочнице), это должен сделать Роман, открыв через локальный сервер.

### Правило самодостаточности каждого шага (закреплено после реального инцидента с CSS)
- **Каждый переданный результат шага обязан быть парой «вынесенный кусок + обновлённый остаток, который на него ссылается» — никогда просто «вынесенный кусок сам по себе»**, лежащий рядом с нетронутым старым кодом, который его дублирует или не знает о его существовании. Проверено на практике: при выносе CSS был отдан только `styles.css` без переписанного `index.html` — предложенная «проверка» ничего не проверяла, потому что нечего было проверять.
- **Единица работы — не «один файл из таблицы», а наименьший набор файлов, при котором получившееся состояние реально запускается и тестируется.** Если файл A нельзя безопасно подключить без файла B (пример: `lib/sortable.js` нельзя подключить как ES-модуль, пока `practice.js`/`practice-router.js` не переведены на модули — иначе `Sortable` будет `undefined` в момент синхронного вызова `hubInitSortable()` при первом рендере хаба, проверено по коду) — A и B выносятся вместе, одним шагом, не порознь.
- Если новый файл технически нельзя ещё подключить к рабочему `index.html` без риска что-то сломать (типичный случай — файл из `core/`, который понадобится нескольким ещё не вынесенным местам сразу) — он не считается «сделанным шагом» до момента реального подключения. Он может быть подготовлен и проверен изолированно (например, через `node` — сверить, что функция даёт те же результаты, что и оригинал), но в чек-листе отмечается выполненным только вместе с тем шагом, где он реально становится частью работающего `index.html`.
- Практическое следствие для Этапа 1: пункты «Подключить ESM-сборку SortableJS» и «Вынести `practice.js`/`practice-router.js`» объединены в один пункт чек-листа — порознь ни один не даёт самодостаточного состояния.

### Принципы структуры папок
- По вкладке — своя папка верхнего уровня (`theory/`, `practice/`, `learnarium/`, `stats/`, `settings/`), названы так же, как вкладки в приложении.
- Файлы называются так же, как тренировки называются в самом приложении, а не по внутренним id.
- Переиспользуемое делится на `core/` (чистая математика/логика, без DOM) и `ui/` (переиспользуемые интерфейсные компоненты).
- `practice/trainings/` — плоская папка, без подпапки на каждую тренировку и без группировки по категориям хаба (та классификация — UI/педагогическая, не структура кода).
- `-logic.js`/`-ui.js` только для тренировок заметно больше ~150–200 строк. **Критерий чистоты:** если в `*-logic.js` встречается `document.getElementById`/`innerHTML` — это сигнал, что код лежит не в том файле.
- `core/state.js` — обязательно чистое хранилище данных, без импортов из фич-модулей — иначе риск циклических зависимостей (например, `state.js` → `settings.js` → `state.js`). Другие модули подписываются на изменения сами (простой Pub/Sub), не наоборот.
- Роутеров — три отдельных, не один: `router.js` (вкладки + «назад», общий), `practice/practice-router.js` (под-экраны Практики), `theory/theory.js` (под-разделы Теории). Раньше это ошибочно считалось одним куском кода в одном диапазоне строк.

### Найденное дублирование и скрытые связи (по факту анализа кода)
- Перемешивание колоды реализовано **трижды**: `shuffle()` (Ауты), `posShuffle()` (Позиции), инлайн-версия в воркере эквити. Объединяются в `core/deck.js`.
- `evaluate5`/`evaluate7`/`displayCategoryIndex` продублированы целиком внутри строки воркера эквити. При переносе — реальный файл, импортирующий `core/hand-eval.js`, все копии удаляются.
- `computeOuts`/`classifyCategories`/`getCoreCards` — уже правильно централизованы и переиспользуются.
- **`evaluate7` на деле универсальна** (работает с 5, 6, 7 и более картами через `combinations(cards, 5)`, не жёстко на 7) — отдельная `evaluate6` не нужна. Название вводит в заблуждение, переименовать в `evaluateBest` при переносе.

Выносится в `ui/card.js` без разделения на отдельные файлы — три функции образуют один тесно связанный слой (`cardEl` вызывает две другие), делить их дальше друг от друга не нужно.

Выносятся преждевременно, не дожидаясь второго случая использования — дёшево сделать сейчас.

### Web Worker и ES-модули
- Нативные Web Workers не понимают `import`/`export` без явного `{ type: 'module' }` при создании. Решение: делать воркер модульным (`new Worker(url, { type: 'module' })`). Альтернатива через `importScripts` рассматривалась, но отклонена в пользу единообразия с остальным ES-модульным кодом. Проверить актуальную поддержку модульных воркеров в целевых браузерах ближе к моменту реализации.
- **Решение по путям импорта исправлено:** не жёсткий абсолютный путь от корня домена (`/js/core/hand-eval.js`) — такой путь сломается, если приложение задеплоено не в корень домена, а в подпапку (например, `username.github.io/pokergym/` на GitHub Pages без кастомного домена — реальный сценарий для Этапа 7). Вместо этого — путь, вычисляемый через `import.meta.url` (относителен фактическому расположению файла воркера, не зависит от глубины подпапки деплоя).
- **Уточнён полный контракт создания воркера (было расписано только для импорта внутри воркера, не хватало второй половины).** Две разные точки, где считается путь, и в каждой — свой способ:
  - **Внутри `core/equity-worker.js`** — импорт `hand-eval.js` по относительному пути: `import { evaluateBest } from './hand-eval.js';`. `equity-worker.js` должен быть полностью автономным файлом, не зависеть от того, откуда его создали.
  - **Внутри `calc-equity.js`** (там, где воркер создаётся) — путь к самому файлу воркера считается через `new URL('../../core/equity-worker.js', import.meta.url)`, и уже этот URL передаётся в `new Worker(url, { type: 'module' })`. `import.meta.url` в этом месте — это URL самого `calc-equity.js`, не воркера, поэтому путь строится относительно него.

### Игровой цикл: прогресс, счёт, обратная связь
- **Подтверждено по коду:** показ прогресса сессии («X / N») продублирован одинаковым паттерном в трёх тренировках (Ауты, Позиции, Комбинации). Счётчик правильных/отвеченных — пока только в «Комбинациях» (`comboState.correctCount`/`answeredCount`), реализован вручную, не как общий модуль.
- Выносится в `core/session.js`. Стандартизированный формат результата хода (успех/неуспех, ответ пользователя, правильный ответ) нужен не только чтобы не копировать код между тренировками, но и потому что Статистике и ачивкам Обучариума (Этапы 4–5) понадобится единый источник данных о ходах — без этого при их реализации пришлось бы либо лезть в код каждой тренировки отдельно, либо получать данные в разном формате от каждой.
- **Согласован формат объекта результата хода** (обычная форма JS-объекта, не TypeScript — в проекте нет TypeScript, `interface` как синтаксическая конструкция в `.js`-файле работать не будет, это была бы ошибка):
  ```js
  // { trainingId: string, isCorrect: boolean, userAnswer: any,
  //   correctAnswer: any, timestamp: number }
  ```
  `trainingId` — совпадает с ID тренировки (`outs`, `positions`, ...), `timestamp` — для будущей аналитики скорости ответов. Каждая `*-ui.js` при обработке ответа передаёт такой объект в `core/session.js`.
- **Важное уточнение контракта `core/session.js` — он не должен трогать DOM.** В монолите подсчёт прогресса жёстко завязан на конкретные DOM-элементы экрана (`#outs-progress` и т.п. по смыслу) — если `session.js` унаследует этот стиль и сам будет искать селекторы, он станет ещё одним UI-модулем и нарушит то же самое правило чистоты, что действует для `core/hand-eval.js` и `core/deck.js`. Контракт: `session.js` — чистый стейт-менеджер (хранит `currentStep`, `totalSteps`, `correctAnswers`, массив логов результатов ходов), при каждом ответе возвращает обновлённое состояние объектом; какие конкретно текстовые поля на экране обновлять — решает и делает вызывающий `*-ui.js`, не `session.js` сам.
- **Не подтверждено по коду, честно как гипотеза:** анимации правильного/неправильного ответа, таймер сессии, «стрейк» (серия подряд правильных ответов) — этого в текущем коде нет ни в одной тренировке. Возможный `ui/game-effects.js` — идея на будущее, не находка дублирования, см. Backlog.

### Правило «глупых» компонентов в `ui/`
- Компоненты в `ui/` (в первую очередь `table-seats.js`, `range-grid.js`, но правило общее для всех) должны только отрисовывать по входным данным и не слушать клики/не знать о проверке ответа. Обработку взаимодействия ведёт вызывающий `*-ui.js` конкретной тренировки. Иначе компонент перестаёт быть переиспользуемым — он окажется завязан на логику одной конкретной тренировки.
- **Конкретизация для `range-grid.js`:** в монолите клик по ячейке грида (5258–5493) не просто меняет цвет — тут же пересчитывает `pfState.selectedCount`, проверяет лимиты раунда и дёргает валидацию ответа. Если вырезать этот код как есть, компонент окажется намертво спаян с логикой «Матрицы префлопа». Контракт: `range-grid.js` принимает на вход матрицу состояний ячеек (объект/двумерный массив, ключ — код руки типа `AA`/`AKs`) и коллбэк `onCellClick`; сам не хранит и не проверяет ничего игрового. Логика клика, пересчёт `pfState`, проверка ответа — остаются в `preflop-grid-ui.js`, он же передаёт коллбэк и инициирует перерисовку. Без этого Обучариум не сможет использовать грид для статического показа диапазона без запуска интерактива — а это и есть исходная причина, зачем компонент вообще выносится отдельно.
- **Конкретизация для `card.js` (проверено по коду — уточнение важное):** сама `suitColor(suit, faceStyle)` уже чистая функция, `faceStyle` приходит параметром, `state` напрямую не читает. Но `cardEl(card, faceUp)` — читает `state.faceStyle` и `state.cardBack` сама, то есть зависимость от глобального состояния есть на уровень выше, чем казалось. Контракт при переносе: `cardEl(card, faceUp, faceStyle, cardBack)` — стиль колоды и рубашка приходят параметрами от вызывающего `*-ui.js`, `ui/card.js` не импортирует `core/state.js` вообще.

### UX: экран настроек тренировки (исходно был пункт в бэклоге, перенесён в решения)

Технический аргумент: заметно упрощает `practice-router.js` — не нужно плодить пару setup/session под-экранов на каждый модуль, один экран тренировки + одна модалка настроек на всех, единая точка входа вида `startTraining(moduleId, customSettings = null)`. Это требование к контракту `startTraining` и к `practice-router.js`, закладывается сразу при разработке роутера, не задним числом на Этапе 4.

### Работа с проектом в чате (без Claude Code) — как реально получать доступ к репозиторию
- Project Knowledge (Документы проекта) — плохая идея для активно редактируемого многофайлового проекта: нет папок, а ниже ~200К токенов Документы грузятся в контекст целиком при каждом сообщении.
- `ARCHITECTURE.md` — небольшой ориентир в Документах (грузится автоматически); отдельный Project для PokerGym — своя изолированная память и поиск.
- **Проверенный на практике рабочий способ чтения кода: `bash_tool` (песочница с обычным `curl`), не `web_fetch`.**
  - `web_fetch` — почти бесполезен для этой задачи: может читать только те URL, что уже явно встречались в разговоре (дал сам пользователь, или пришли из предыдущего поиска/фетча) — принципиальное ограничение безопасности самого инструмента (защита от утечки данных через промпт-инъекции), действует с момента появления инструмента, не «недавно ввели». Самостоятельно построить и открыть новый URL (даже зная его наверняка) через `web_fetch` невозможно в принципе.
  - `bash_tool` — отдельная песочница с собственным сетевым доступом, ограниченным списком разрешённых доменов, среди которых есть `github.com`, `raw.githubusercontent.com`, `api.github.com`, `codeload.github.com`. Это ограничение `web_fetch` на него не распространяется — можно просто выполнить `curl <URL>` на любой путь внутри этих доменов, включая ссылки, которые никто не присылал.
  - Практическая команда для чтения любого файла репозитория:
    ```
    curl -s "https://raw.githubusercontent.com/Ramzesikus/PokerGym/main/путь/к/файлу"
    ```
    Работает без ссылки от пользователя, без ограничений — подтверждено на `css/styles.css` и `index.html`.
  - `api.github.com` (например, `git/trees/main?recursive=1` — список всех файлов репозитория одним запросом) технически доступен тем же способом (`curl` из `bash_tool`), но подвержен общему лимиту запросов GitHub на IP-адрес — у песочницы IP, видимо, общий на многих пользователей разом, поэтому запрос может временно упираться в лимит (`API rate limit exceeded`). Если это произошло — просто попробовать ещё раз чуть позже, либо сразу читать нужные файлы напрямую через `raw.githubusercontent.com` по путям, уже известным из этой таблицы, не дожидаясь списка.
  - Требует публичного репозитория — если сделать приватным, оба домена перестанут отдавать содержимое.

### Claude Code
- Работает напрямую с файлами на диске, `CLAUDE.md` в корне читается автоматически. Начинать можно в любой момент. Доступен из терминала, десктоп-приложения, браузера («Claude Code on the web» — отдельная облачная песочница), мобильного приложения. Рекомендуется изоляция при автономном режиме — использовать простаивающую VM с Ubuntu в VirtualBox. Сессия не видит переписку в обычном чате — план копировать явно, лучше сразу в `CLAUDE.md`. Пока не переходим.

### PWA
- PWA = сайт + `manifest.json` + service worker. Сейчас ни того, ни другого нет. Известная болячка — обновление закэшированной версии без продуманного версионирования. Поддержка PWA у Apple менее стабильна, чем у Google/Android.

### Деплой
- Деплой происходит по `git push`, не по каждому визиту. Публичность репозитория и публичность сайта — независимые вещи. Минификация — часть сборки, которой сейчас нет в проекте. Файлы репозитория при деплое остаются нетронутыми.

### Приватность репозитория
- Публичный репозиторий, пока в нём только клиентская логика — риск низкий. Автоматические боты сканируют все публичные репозитории на предмет секретов — секреты не коммитить никогда. Закрыть репозиторий — когда появится код авторизации/оплаты.

### Целевая архитектура ресурсов
- Три слоя: хостинг статики → сервер API → база данных. Начинать с управляемых отдельных сервисов, не с одного своего сервера.

### localStorage
- Формат — JSON. Чисто локальные предпочтения (язык, тема, порядок хаба) — только `localStorage`. Данные аккаунта (подписка, прогресс, статистика) — источник правды сервер/БД, `localStorage` — кэш для офлайн/скорости, синхронизация при подключении. Сейчас `localStorage` не существует вообще.

### Защита
- Обязательная (пароли/HTTPS/токены/платёжный провайдер) — стандартные средства. Защита от копирования — принципиально не стопроцентная. Стратегия: «сделать бесполезным без сервера», не «сделать невозможным» — ценная логика (генератор Обучариума) переносится на сервер. Конфликт целей: офлайн-режим vs частая ревалидация лицензии — компромисс, ограниченный офлайн-срок. Простая мера сейчас — лимит одновременных сессий. Водяные знаки — отложено до признаков реальной проблемы. Юридическая мера — пользовательское соглашение. Общая калибровка: серьёзная защита кода — практика крупных игроков в конкурентных нишах, для небольшого продукта — дешёвый минимум сейчас, дорогие меры по факту необходимости.

### App Store / Google Play
- Android — TWA, Bubblewrap/PWABuilder, 80+ баллов Lighthouse, 25$ разово. iOS — менее стабильная поддержка PWA у Apple, реалистично нативная обёртка с WebView, 99$/год, решение отложено.

### Хранение пользовательских данных
- Внутренние данные приложения (статика) vs внешние данные пользователей (сервер+БД) — разная инфраструктура. Пароли — только хешированные. Открытый вопрос: требования 152-ФЗ о хранении персональных данных в РФ — проверить отдельно, не юридическая консультация.
